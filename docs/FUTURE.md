# Antflow Sales OS — Future Considerations

Ideas, gaps, and deferred decisions surfaced during real work on this project — not a commitment, not scheduled. The point is that a good idea only has to be raised once; it lives here instead of getting lost or re-litigated from scratch. Move an item out (and delete it here) when it's actually built, or when it's deliberately decided against — don't let this become a graveyard nobody reads.

## AI Employee Runtime

- **Ebook content search (phase 2 of the FAQ work)** — deferred in favor of a curated FAQ first (safer for health-adjacent claims, cheaper, covers the predictable question set). Only build real on-demand search over the ebook's chunked content if real customers start asking things the FAQ can't cover.
- **Quiet-hours enforcement** — `BusinessConfig.businessHours` already exists in the schema but nothing reads it; follow-ups can currently fire at 3am.
- **Human escalation after full follow-up exhaustion — partially done.** A sequence that exhausts because the customer claimed to have paid but never sent evidence (`reason: AWAITING_PAYMENT_EVIDENCE`) now escalates to a human instead of auto-tagging "Uninterested". A cold pitch that just goes unanswered (`reason: GENERAL`) still auto-tags "Uninterested" and marks `LOST_LEAD` with no human glance — worth reconsidering if that turns out to be writing off real leads.
- **Follow-up counter fully resets on any reply** — a customer who replies once (even just "ok") and then ghosts again gets a brand-new step-1 sequence, with no memory of how many times this has already happened this conversation. A customer who's mildly responsive but never actually commits could in principle get followed up forever, never hitting the 5-step exhaustion that leads to `LOST_LEAD`/escalation. Left as-is deliberately (a reply is a genuinely new situation, not just a continuation of the old silence) — revisit only if this pattern actually shows up in real customer behavior, e.g. by capping total follow-up attempts per conversation lifetime, not just per unbroken silence.
- **Follow-up effectiveness analytics** — a Home KPI for "follow-ups sent → % converted" would show whether the cadence is actually working.
- **Per-conversation pause follow-ups button** — the business-wide toggle (Settings) only has one lever: everything on or everything off. The only way to silence follow-ups for one specific customer today is to mark the conversation Resolved or escalate it to a human, both of which do more than intended just to quiet one person down. Needs a `Conversation.followupsPaused` boolean (not `Customer`-level — follow-ups are conversation-scoped, and this app treats a conversation as the durable ongoing thread), checked at the same two enforcement points as the business-wide flag (the worker before sending, `createFollowup` before scheduling), plus a button on the Dashboard Review page (`/dashboard/[id]`) alongside the existing "Mark resolved" action.
- **Follow-up fallback template has no dynamic content** — outside the 24-hour customer service window, `deliverFollowup` (followup-worker.ts) can only send the one fixed, Meta-approved `WHATSAPP_FOLLOWUP_TEMPLATE_NAME` template, and `sendWhatsAppTemplate` only takes a name/language, no variables — so even when a real blocker is recorded as a fact (e.g. "customer couldn't open the PDF"), a follow-up firing outside the window can never reference it, only the generic "still interested?" line. Fixing this needs two things together: a *new* Meta-approved template built with a `{{1}}`-style variable placeholder (external approval, not just code), and passing `components` through `sendWhatsAppTemplate` so `deliverFollowup` can fill it from the conversation's recorded facts. Deferred until the pure-code follow-up fixes (fact-recording reliability, sequence length, stop-on-decline) are done — revisit then, not before.
- **Gemini vs. Claude tone comparison** — one informal test suggested Gemini may score better on Nigerian Pidgin/cultural nuance specifically, separate from Claude's proven strength at strict tool-use rule-following. Not rigorous; revisit once there's a real side-by-side against actual sample conversations. The Action Contract/Conversation Brain architecture is provider-agnostic enough that swapping only the conversational model is plausible without a rebuild.

## Dashboard / CRM

- **Pipeline/kanban board view** — all conversations grouped by stage as columns, the standard CRM bird's-eye pattern; today you can only see one conversation's stage at a time.
- **Stage-based filter rail on the Conversations list** — a left-hand filter (New Lead / Product Selected / Payment / Delivered / Completed, each with a count) so a human can jump straight to, say, everyone stuck at Payment, instead of scanning one flat list. Maps directly onto the existing `ConversationStage`/`PIPELINE_MILESTONES` — spotted while comparing against respond.io's inbox UI (lifecycle filters in their nav rail).
- **Internal team notes on a conversation** — a way for a human to leave a free-text note for whoever picks up the conversation next ("returning customer, reported X"), visible to the team but never sent to the customer. Distinct from the existing structured facts/summary; today there's no equivalent at all. Also from the respond.io comparison — their inbox has a separate "comment" mode alongside the customer-facing reply box.
- **Inline system/event log in the conversation timeline** — stage changes, escalations, and tags-added are already recorded (`Event` model) but invisible on the Review page; a human can't currently see *why* a conversation moved stage without digging. Surfacing key events inline in the message thread (e.g. "Stage updated to Hot Lead", "Escalated to human") would make Review self-explanatory at a glance.
- **Connection health indicator** — the WhatsApp webhook/token silently breaking is invisible until a real customer complains (this already happened once). A "webhook last received: X ago, token status: OK" card would catch it immediately.
- **Ad performance (ROAS/spend) in the Trends page** — wanted eventually, not now (confirmed with the business owner, 2026-08-22). Would need the Marketing API, which needs its own scoped access — deliberately *not* granted to the WhatsApp system user when this came up (Business Settings → System users → the ad account asset), since that token's only job today is messaging + Conversions API reporting, and Marketing API read access is a different permission for a different, not-yet-built feature. When this gets built: either grant `ads_read` on the relevant ad account to the existing system user, or create a separate one scoped to just that — least-privilege either way, don't default to reusing the messaging token's broader access.
- **Usage/cost visibility in-app** — the Opus→Sonnet cost issue was caught by the user noticing it in the Anthropic Console, not from anything in this dashboard. A "conversations this month, spend this month" tile is cheap and closes that blind spot. Looked into an ElevenLabs-style ring meter (avatar with a ring showing % of credit remaining, counting down to zero) and confirmed it isn't buildable against real data: Anthropic has no API for remaining credit balance — someone requested exactly this (even just for a status line) and Anthropic closed it as not planned; balance is Console-only. What *does* exist is the Usage & Cost Admin API (`/v1/organizations/usage_report/messages`), which reports spend, not balance — it needs a separate Admin API key (`sk-ant-admin...`, org-admin-only to create) distinct from the runtime's regular API key. A ring needs both a numerator (spend, real) and a denominator (budget, not real) to show a percentage, so the two honest options are: (a) show spend-to-date as a plain number/trend, no ring, no invented "remaining" figure — matches this app's general stance against presenting approximations as precise (see the payment-confirmation Non-Negotiable, PRD 14.2); or (b) build the ring anyway against a manually-entered budget figure in Settings, clearly a self-reported target rather than a true balance reading, which will drift if top-ups are irregular. Deferred without a decision between the two — revisit when cost visibility actually becomes a recurring pain point, not just a one-off surprise.
- **Dark mode toggle** — shadcn's `.dark`-class tokens are already wired up, but no toggle exists; the app is deliberately light-only since every reference design provided was light-mode. Build if asked.

## App Shell / UI

- **Skeleton loading states on navigation** — built and then reverted (Dashboard, Customers, Home, conversation Review all got a `loading.tsx` + matching skeleton content). The catch: `AppShell` isn't a persistent Next.js layout, it's called inline inside every `page.tsx` and does its own business/numbers/notification queries on each navigation — so the sidebar suspends and shimmers along with the page content instead of staying static and interactive the way it does on the platforms this was modeled after (Claude Console, ElevenLabs). Doing it properly means first converting `AppShell` into a real layout (a `(protected)` route group wrapping Dashboard/Customers/Home/Manage/Settings), which also has a genuine perf upside — those chrome queries would run once per session instead of once per page load — but it's a real routing refactor touching all ten pages' `title`/`description`/`actions` wiring, not a same-session addition. Pulled rather than shipped a version that only half-matched the reference platforms. Revisit skeleton loading states together with that layout refactor, not before it.

## Multi-Branch Support

- **First-class `Branch` entity + per-agent access enforcement** — the business now runs two WhatsApp numbers as two branches (`Business.whatsappPhoneNumberId`/`additionalWhatsappPhoneNumberIds`, `Conversation.whatsappPhoneNumberId`), with Home/Conversations/Customers all scoped to whichever branch the sidebar switcher selects (a cookie — `src/lib/number-filter.ts`). That scoping is currently just a UI default, not real access control: any logged-in team member can switch the sidebar to either branch, and nothing at the query level stops them. A proper version would add a real `Branch` model (id, businessId, an actual name, its phone_number_id, room for branch-specific config later — hours, escalation thresholds, etc.), a real `Conversation.branchId` foreign key instead of a loose string match, and a `HumanAgent` → branch relationship enforced server-side (not just defaulted in the UI). Deferred because nothing is being harmed by the gap today — small team, presumably already trusted with full visibility — and production currently has ~0 customers, so the eventual migration/backfill is as cheap as it will ever be. **Trigger to revisit: the moment a login is about to be created for someone who should be restricted to only one branch** — build the real model before that onboarding, not after they're already using the system.

## Infrastructure

- **WhatsApp access token expiry monitoring, then switch to a 60-day token** — the WhatsApp System User token (`WHATSAPP_ACCESS_TOKEN`) is currently set to never expire, chosen specifically because nothing in this app monitors or alerts on token expiry: a 60-day token (Meta's own recommended default) would silently take down the entire WhatsApp integration — every AI response, payment confirmation, follow-up — the moment it lapsed, with no warning to anyone. Never-expiring is the worse security posture (a leaked token stays valid forever until manually revoked) but the safer operational one today. Revisit once there's actual expiry monitoring/alerting in place (e.g. a health-check that warns days before expiry), at which point a 60-day token becomes the strictly better choice on both fronts.
- **R2 custom domain** — currently serving receipt images via the bucket's `r2.dev` public development URL, which Cloudflare flags as rate-limited and meant for lighter use. Fine at current traffic; move to a real custom domain if volume grows.
- **Git remote's embedded PAT** — the `sales_os` GitHub remote URL has a personal access token embedded directly in it (local `.git/config`, never committed/leaked publicly, but still worth cleaning up via `gh auth` or Windows Credential Manager eventually).
- **Node 20 → 22** — the AWS SDK v3 (used for R2 storage) warns that versions published after early January 2027 will require Node ≥22; Railway is currently on 20. Not urgent, but a real deadline exists.
